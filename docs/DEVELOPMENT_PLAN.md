# 类京东电商平台开发规划流程文档

## 1. 项目定位

本项目计划构建一个大规模、多端、前后端分离的电商平台，能力范围类似京东的核心交易与后台管理体系。系统覆盖用户网页端、Android App、商家后台、管理员后台，后端使用 FastAPI，数据库使用 PostgreSQL，前端使用 React + Next.js + Tailwind CSS。

开发原则是“核心流程做深，非核心流程模拟”。例如支付可以先做模拟支付和支付适配层，但订单、库存、售后、权限、客服介入、多端状态同步必须按真实业务复杂度设计。每个被选定为重点的业务流程都要有状态机、异常路径、权限边界、审计日志和可回归测试。

## 2. 总体目标

业务目标：

- 普通用户可以完成浏览商品、搜索筛选、购物车、结算、模拟支付、查订单、申请售后。
- 商家可以管理店铺商品、库存、订单发货、售后审核、账单结算。
- 平台管理员可以做用户/商家/商品/订单/售后/客服/风控/财务治理。
- 不同角色之间的操作可以联动，例如用户申请退款、商家处理、平台客服介入、系统超时自动推进。

工程目标：

- 采用 monorepo 管理多端和后端。
- 通过 OpenAPI 维护前后端契约。
- 通过 PostgreSQL migration 管理数据库演进。
- 通过 Git 分支、PR、CI、阶段 release 管理多人/多 agent 协作。
- 每个阶段完成后提交并推送远端仓库。

## 4. 核心业务域

账号与身份域：

- 用户注册登录、手机号/邮箱、地址簿、设备登录、会员等级。
- 管理员、商家员工、用户账号隔离。
- 会话、JWT、刷新令牌、登录态过期处理。

商品域：

- SPU/SKU、品牌、类目、规格、图片、详情、价格。
- 商品上下架、审核、可售区域、商家维度归属。
- 商品详情快照，避免订单历史随商品修改而变化。

搜索与推荐域：

- 关键词搜索、筛选排序、热词、基础推荐位。
- 早期可以用数据库搜索或轻量搜索服务，后续再接专业搜索引擎。

购物车与结算域：

- 购物车增删改查、选中状态、SKU 失效提醒。
- 结算时重新计算价格、库存、运费、地址可配送性。
- 下单前必须处理价格变化、优惠失效、库存不足。

订单域：

- 订单和子订单，支持按商家、仓库或包裹拆分。
- 订单价格快照、收货地址快照、商品快照。
- 订单状态机、支付超时关闭、库存预占释放。

库存与履约域：

- 库存锁定、释放、扣减、补偿。
- 商家发货、物流单、签收、拒收、自动收货。
- 并发下单和支付超时是重点测试场景。

支付与资金域：

- 当前阶段做模拟支付，但接口设计要保留真实支付适配层。
- 支付单、退款单、支付回调、退款重试、对账记录。
- 支付和退款回调必须支持重复、乱序和补偿查询。

售后域：

- 仅退款、退货退款、换货/维修可后续扩展。
- 商家审核、用户寄回、商家收货、平台客服介入。
- 超时任务、证据链、工单、裁决、审计日志。

商家域：

- 商家入驻、店铺资料、员工权限、商品运营、订单履约、售后、结算。

后台治理域：

- 商品审核、订单查询、客服工单、风控、财务复核、报表、系统配置。

## 5. 角色与权限设计

权限模型至少包含四层：

- 菜单权限：是否能看到某后台页面。
- 接口权限：是否能调用某 API。
- 数据范围权限：能看哪个店铺、哪个商家、哪个区域、哪个工单队列。
- 字段权限：手机号、地址、支付流水等敏感字段脱敏。

用户角色：

- 普通用户：浏览、下单、支付、订单、售后、评价。
- 会员用户：会员价、专属券、优先售后等扩展。
- 企业用户：发票、批量采购、子账号审批等扩展。

商家角色：

- 店主：店铺设置、员工管理、结算查看。
- 商品运营：商品发布、改价、库存、活动报名。
- 订单客服：订单查询、修改地址、售后初审。
- 仓储发货：待发货订单、打印面单、物流录入。
- 财务：账单、提现、发票、对账；不能修改商品和订单核心状态。

管理员角色：

- 超级管理员：系统配置、权限分配、审计。
- 平台运营：类目、活动、内容位、商品审核。
- 客服：工单处理、售后裁定、补偿券发放。
- 客服主管：复杂工单升级、客服绩效、批量裁定复核。
- 风控审核：账号、订单、支付风险处置。
- 财务管理员：退款复核、商家结算、渠道对账。
- 技术管理员：系统配置、任务监控、日志查看，不直接处理业务资金。
- 只读审计：查看日志和报表，不能执行业务操作。

所有敏感操作必须记录：操作人、角色、来源 IP、对象、前后状态、原因、凭证、时间。

## 6. 订单状态机

订单主状态建议：

```text
待支付
  -> 已支付待发货
  -> 已发货待收货
  -> 已完成

待支付
  -> 已关闭

已支付待发货
  -> 已关闭        # 取消且退款完成
  -> 售后处理中

已发货待收货
  -> 售后处理中
  -> 已完成
```

关键规则：

- 创建订单后锁定库存，进入 `待支付`。
- 支付超时自动关闭订单并释放库存。
- 支付成功后扣减或确认占用库存，进入 `已支付待发货`。
- 商家发货后进入 `已发货待收货`，绑定物流单。
- 用户确认收货或系统自动收货后进入 `已完成`。
- 已完成订单可评价，可在售后时效内申请售后。
- 风控关闭、用户取消、未支付超时、退款完成都要区分关闭原因。

订单必须支持：

- 订单维度和子订单维度状态。
- 拆单后按包裹发货、按子订单售后。
- 价格、地址、商品、发票信息快照。
- 幂等创建、幂等支付回调、幂等取消。

## 7. 售后与退款流程

售后状态建议：

```text
申请中
  -> 商家待处理
  -> 待买家退货
  -> 待商家收货
  -> 退款处理中
  -> 退款成功

商家待处理
  -> 商家拒绝
  -> 客服介入中
  -> 售后关闭

退款处理中
  -> 退款失败
  -> 人工处理
```

正常路径：

1. 用户提交退款/退货申请，填写原因、金额、数量、凭证。
2. 商家审核，同意后进入仅退款或待买家退货。
3. 用户寄回商品并填写物流。
4. 商家确认收货。
5. 系统生成退款单，模拟支付渠道退款。
6. 退款成功后同步订单、售后单、资金流水、消息通知。

异常路径：

- 商家超时不审核：自动同意或升级客服，规则由后台配置。
- 商家拒绝：用户可补充凭证、撤销、再次申请或申请客服介入。
- 用户超时不退货：售后自动关闭，但需要保留再次申请规则。
- 商家超时不收货：自动确认收货并推进退款。
- 退款失败：进入可重试或人工处理，保留渠道错误码。
- 物流异常：支持用户修改物流单号、客服介入、商家举证。

客服介入机制：

- 生成工单，关联订单、售后单、双方证据。
- 客服可要求补充凭证、裁定同意退款、裁定驳回、发放补偿券。
- 客服不能绕过财务复核直接处理超大金额退款。
- 裁定结果必须通知用户和商家，并写入审计日志。

## 8. 用户端体验要求

用户网页端和 Android App 都要覆盖：

- 首页、分类、搜索、商品详情、购物车、结算、订单列表、订单详情、售后申请。
- 登录态过期时保留当前操作上下文。
- 商品失效、库存不足、价格变化、地址不可配送要有明确提示。
- 支付成功但页面断网、回调延迟时，订单页要能主动刷新状态。
- 售后申请中要清楚展示当前进度、下一步动作、超时剩余时间。

UI 原则：

- 用户端可以更视觉化，但第一屏必须让用户直接购物，不做空泛介绍页。
- 列表、筛选、价格、库存、物流、售后进度要易扫读。
- 移动端优先考虑单手操作、弱网、回退、状态恢复。

## 9. 商家后台体验要求

商家后台是工作台，不是营销站点。页面应当紧凑、清晰、可批量处理。

重点流程：

- 商品发布和审核状态查看。
- SKU 价格、库存、上下架管理。
- 待发货订单批量处理、打印面单、物流录入。
- 售后待处理队列，按超时风险、金额、原因筛选。
- 结算账单、退款记录、平台佣金。

体验细节：

- 售后列表必须显示剩余处理时间和风险等级。
- 订单详情页要同时显示用户诉求、商家操作区、平台规则提示。
- 拒绝售后必须选择原因并上传凭证。
- 对批量发货、批量改库存等高风险操作做二次确认。

## 10. 管理员后台体验要求

管理员后台覆盖平台客服、运营、风控、财务、技术管理员等细分角色。

重点流程：

- 客服工单：售后争议、订单异常、用户投诉。
- 商品治理：商品审核、违规下架、类目管理。
- 商家治理：入驻审核、资质查看、店铺处罚。
- 风控：异常账号、异常订单、频繁退款、疑似刷单。
- 财务：退款复核、商家结算、渠道对账。
- 审计：操作日志、权限变更日志、敏感数据访问日志。

体验细节：

- 后台首页按角色展示待办，而不是所有人看到同一个仪表盘。
- 客服处理工单时要看到完整时间线和证据链。
- 风控和财务操作必须有原因、审批、审计和回滚或补偿方案。
- 只读角色不能触发任何状态改变。

## 11. 后端架构规划

FastAPI 结构建议：

```text
apps/api/
  app/
    main.py
    core/
      config.py
      logging.py
      security.py
    api/
      v1/
        routers/
          auth.py
          catalog.py
          cart.py
          orders.py
          after_sales.py
          merchant.py
          admin.py
    domains/
      order/
        models.py
        schemas.py
        service.py
        state_machine.py
        repository.py
      after_sales/
      inventory/
    db/
      session.py
      base.py
    tests/
```

后端约定：

- 路由层只做输入输出、鉴权依赖、错误映射。
- 服务层负责业务规则、状态迁移、事务编排。
- repository 层负责数据库访问。
- 状态机规则集中管理，不散落在路由里。
- 使用数据库事务和唯一约束保证幂等。
- 所有后台操作必须写审计日志。

## 12. 数据库规划

核心表可逐步演进：

- `users`、`user_addresses`、`roles`、`permissions`、`role_permissions`、`user_roles`
- `merchants`、`merchant_users`、`shops`
- `categories`、`brands`、`spus`、`skus`、`sku_inventory`
- `carts`、`cart_items`
- `orders`、`order_items`、`order_status_events`
- `payments`、`refunds`
- `shipments`、`shipment_events`
- `after_sales_requests`、`after_sales_events`
- `work_orders`、`work_order_comments`
- `audit_logs`、`notifications`

关键设计：

- 金额使用整数分或定点类型，禁止浮点。
- 订单保存商品、价格、地址快照。
- 状态事件表记录每次状态迁移。
- 高并发库存操作使用事务、行锁、乐观锁或库存流水。
- 后台查询要预留索引和分页。

## 13. 前后端契约

契约原则：

- OpenAPI 是接口事实来源。
- 后端每次接口变更都要生成或更新类型。
- 前端和 Android 不手写与接口不一致的 DTO。
- breaking change 必须写入 ADR 或 release note。

接口版本：

- 初期使用 `/api/v1`。
- 管理端和商家端可在同一 API 版本下通过权限区分，也可按 router 分组。
- Web 管理端不要依赖数据库内部字段。

## 14. 测试策略

后端测试：

- 单元测试：状态机、权限判断、价格计算、库存计算。
- 集成测试：PostgreSQL、migration、订单下单、支付回调、退款流程。
- 契约测试：OpenAPI schema、错误码、分页、权限。

Web 测试：

- 单元/组件测试：表单、表格、权限渲染、状态组件。
- Playwright E2E：登录、下单、支付模拟、售后申请、商家审核、客服介入。
- 视觉检查：后台复杂表格、移动端布局、弹窗不遮挡。

Android 测试：

- ViewModel/unit tests。
- 关键页面 screenshot tests。
- 登录、商品详情、购物车、订单、售后流程 instrumentation tests。

业务回归重点：

- 下单前后价格变化。
- 秒杀或多人抢同一 SKU。
- 支付成功但前端断网。
- 重复支付回调。
- 部分退款和优惠分摊。
- 商家越权查看其他店铺订单。
- 客服越权直接退款。
- 用户、商家、管理员三端状态刷新一致。

## 15. CI/CD 与质量门禁

CI 至少包含：

- Python 格式化、lint、类型检查、pytest。
- Alembic migration upgrade 检查。
- Web lint、typecheck、build。
- Android lint、unit test、build。
- OpenAPI diff。
- Docker Compose smoke test。

合并规则：

- PR 至少 1 人 review。
- CI 全绿。
- 涉及 API、DB、权限、核心流程的 PR 必须更新文档或测试。
- `main` 只接受 `release/*` 或 `hotfix/*`。

发布规则：

- 每个 milestone 完成后创建 release 分支。
- release 分支只接受修复和文档补充。
- 验收通过后打 tag，例如 `v0.1.0-m0`。
- tag 和 `main` 必须推送远端。

## 16. 阶段里程碑

### M0 基建

目标：

- 建立 monorepo、FastAPI 空服务、Next.js 空壳、Android 空壳。
- Docker Compose 启动 PostgreSQL 和 API。
- CI 初版、代码风格、基础 README。

交付物：

- `apps/api` health check。
- `apps/web` 基础页面。
- `apps/android` 可构建工程。
- `infra/docker` 和 `.env.example`。
- `develop`、`release/milestone-0-foundation`、tag。

### M1 账号与权限

目标：

- 完成用户、商家员工、管理员账号体系。
- 完成 RBAC、登录、会话、基础审计。

交付物：

- 登录/注册 API。
- 管理员和商家后台登录页。
- 权限中间件和测试。
- 角色权限矩阵文档。

### M2 商品与库存

目标：

- 完成商品、类目、SKU、库存基础能力。
- 用户端商品列表和详情，商家端商品管理。

交付物：

- 商品 API、库存 API。
- 商家商品管理页面。
- 用户商品浏览页面。
- 库存并发基础测试。

### M3 购物车、订单、模拟支付

目标：

- 完成购物车、结算、订单创建、模拟支付、订单状态机。
- 实现库存锁定、支付超时、订单关闭。

交付物：

- 购物车和结算 API。
- 订单状态机。
- 用户端下单流程。
- 订单回归测试。

### M4 售后、商家后台、管理员后台

目标：

- 深入实现售后退款、商家审核、客服介入。
- 补全商家后台和管理员后台核心工作台。

## 17. Multi-Agent 执行流程

建议每个大任务按以下方式拆解：

1. `docs-agent` 先写业务流程、状态机、权限矩阵或 ADR。
2. `backend-agent` 根据文档实现 API、DB、状态机和 OpenAPI。
3. `web-user-agent`、`web-merchant-agent`、`web-admin-agent` 分别实现端侧页面。
4. `android-agent` 实现移动端核心链路。
5. `qa-agent` 补充跨端 E2E 和回归用例。
6. `infra-agent` 确保 CI、Docker、本地启动脚本可用。
7. 阶段验收后合并、tag、推送远端。

任务拆分必须保证写入范围尽量不重叠。需要跨域变更时，先在 PR 描述中说明影响面。
