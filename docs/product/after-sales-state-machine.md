# M4 After-Sales State Machine

本文档定义 M4 售后、退款、商家处理、管理员客服介入和后台联动规则。M4 的目标不是把所有售后品类一次做完，而是把退款、退货退款、客服工单、超时任务、审计和权限边界做深，保证用户端、商家后台、管理员后台看到同一业务事实。

## 1. 范围与原则

M4 覆盖：

- 用户在可售后时效内提交仅退款或退货退款申请。
- 商家审核同意、拒绝、要求补充凭证。
- 用户补充凭证、申请客服介入、撤销售后、填写退货物流。
- 商家确认收货、拒收或标记异常。
- 系统创建模拟退款单，处理退款成功、失败、重试和人工处理。
- 平台客服工单介入、要求双方补充凭证、裁定同意或驳回。
- 商家超时自动同意或自动升级客服，用户超时未退货自动关闭，商家收货超时自动确认。
- 用户、商家、管理员权限联动、字段脱敏、审计日志和消息通知。

M4 暂不覆盖：

- 真实第三方退款渠道清结算。
- 换货、维修、价保、发票红冲的完整闭环。
- 多级审批流引擎；M4 只定义必要的财务复核和客服主管复核入口。
- 复杂促销的最终财务算法实现；但必须预留优惠券、运费、组合商品和部分退款分摊字段。

设计原则：

- 售后单、退款单、客服工单是三个独立对象，状态互相关联但不能互相替代。
- 任何角色不得绕过状态机直接改售后、退款或订单状态。
- 每个状态迁移必须有触发人、原因、证据、幂等标识和事件记录。
- 超时任务必须可重复执行，重复扫描不能重复退款、重复关闭或重复生成工单。
- 敏感操作必须审计，敏感字段访问必须按角色和工单上下文脱敏。
- 用户端、商家端、管理员端展示同一售后事实，但操作入口、字段范围和文案按角色区分。

## 2. 核心对象

| 对象 | 说明 | 关键要求 |
|---|---|---|
| `after_sales_request` | 售后单 | 绑定用户、订单、订单行、商家、售后类型、申请金额、数量、原因、当前状态 |
| `after_sales_event` | 售后状态事件 | 记录前后状态、触发人、原因、证据摘要、幂等键和时间 |
| `refund` | 退款单 | 绑定售后单和支付单，保存退款金额、模拟渠道号、状态和失败原因 |
| `work_order` | 客服工单 | 绑定订单、售后单和双方证据摘要，保存队列、优先级、处理人、结论、内部备注 |
| `audit_log` | 审计日志 | 记录敏感操作、权限拒绝、字段访问、客服裁决、财务处理 |
| `notification` | 消息通知 | 通知用户、商家、客服、财务和风控待办变化 |

M4 当前实现把售后商品行合并到 `after_sales_request.order_item_id + quantity`，把退货物流字段保存在售后单上，把工单沟通先沉淀为 `work_order.evidence_summary` 和 `work_order.internal_notes`。后续 M5 或更深阶段再拆出 `after_sales_item`、`refund_event`、`return_shipment`、`work_order_comment` 和 `notification` 专表。

金额必须使用整数分或定点类型。售后单应保存申请金额、数量、原因、证据、退款失败原因；运费承担方、优惠分摊和组合商品退款明细属于后续深化项。

## 3. 售后类型

| 类型 | 适用订单状态 | 核心路径 | 备注 |
|---|---|---|---|
| `refund_only` | `paid_pending_shipment`、未发货或约定无需退货场景 | 商家审核或客服裁定后直接退款 | 常用于未发货退款、缺货、差价补偿 |
| `return_refund` | `shipped_awaiting_receipt`、`completed` 且在售后时效内 | 商家同意后用户退货，商家收货后退款 | 必须有退货物流和收货确认 |

同一订单行的可售后数量不能超过已购买数量减去已成功退款或正在处理的数量。重复申请、部分退款、组合商品退款必须按订单行锁定可售后数量，避免并发售后超退。

## 4. 售后单状态机

售后单主状态：

```text
merchant_review
  -> waiting_buyer_return
  -> refunding
  -> rejected
  -> customer_service
  -> closed

rejected
  -> merchant_review
  -> customer_service
  -> closed

waiting_buyer_return
  -> waiting_merchant_receipt
  -> customer_service
  -> closed

waiting_merchant_receipt
  -> refunding
  -> customer_service

refunding
  -> refund_failed
  -> refunded

refund_failed
  -> refunding
  -> customer_service
```

终态：

- `refunded`：退款完成，售后成功关闭。
- `closed`：售后关闭，必须保存关闭原因，例如用户撤销、用户超时未退货、客服驳回、重复申请被拒。

禁止迁移：

- `refunded` 不能回退为处理中或关闭。
- `closed` 不能重新打开；用户如仍在规则允许范围内，需要创建新售后单并关联历史记录。
- `refunding` 之后商家不能再拒绝售后。
- 已生成退款单后，普通用户和商家不能修改退款金额。
- 商家不能把跨店铺售后单推进任何状态。

## 5. 状态迁移规则

| 当前状态 | 目标状态 | 触发方 | 条件 | 事件与通知 |
|---|---|---|---|---|
| `null` | `merchant_review` | 用户 | 本人订单、售后时效内、可售后数量和金额有效 | 售后创建事件，通知商家，计算审核截止时间 |
| `merchant_review` | `refunding` | 商家或客服 | 仅退款审核同意，金额合法 | 写审核事件，创建退款单，通知用户 |
| `merchant_review` | `waiting_buyer_return` | 商家或客服 | 退货退款审核同意，需要退货 | 写审核事件，通知用户填写物流 |
| `merchant_review` | `rejected` | 商家 | 必须填写拒绝原因并上传凭证或规则依据 | 写拒绝事件，通知用户可补证或申请客服 |
| `merchant_review` | `rejected` | 商家 | 当前证据不足，需明确补充材料类型和截止时间 | 写补证要求事件，通知用户 |
| `merchant_review` | `customer_service` | 用户、系统任务或客服 | 用户申请介入，或商家超时按规则升级 | 创建或关联工单，通知双方 |
| `rejected` | `rejected` | 用户 | 用户选择补充凭证而非直接介入 | 写补证待处理事件 |
| `rejected` | `merchant_review` | 用户 | 上传新凭证、说明或修改申请信息 | 重置或缩短商家审核截止时间，通知商家 |
| `rejected` | `customer_service` | 用户 | 用户不同意拒绝结果并申请平台介入 | 创建工单，冻结商家同意/拒绝入口 |
| `rejected` | `closed` | 用户或系统 | 用户撤销，或拒绝后申诉窗口超时 | 写关闭事件 |
| `waiting_buyer_return` | `waiting_merchant_receipt` | 用户 | 填写有效退货物流，必要时上传凭证 | 通知商家关注收货 |
| `waiting_buyer_return` | `closed` | 系统任务 | 用户退货截止时间到期且未填写物流 | 写超时关闭事件，通知双方 |
| `waiting_merchant_receipt` | `refunding` | 商家或系统任务 | 商家确认收货，或商家收货超时自动确认 | 创建退款单，通知用户和财务可见 |
| `waiting_merchant_receipt` | `customer_service` | 商家、用户或系统 | 商家拒收、物流异常、双方争议 | 创建工单，通知客服 |
| `refunding` | `refunded` | 模拟退款回调或补偿查询 | 退款金额匹配，退款单成功 | 写售后和退款事件，通知用户和商家 |
| `refunding` | `refund_failed` | 模拟退款回调 | 渠道失败、账户异常、金额异常或超时失败 | 写失败码和可重试标识，通知财务 |
| `refund_failed` | `refunding` | 系统任务或财务管理员 | 失败可重试且未超过重试上限 | 写重试事件，幂等请求退款 |
| `refund_failed` | `refund_failed` | 系统任务或财务管理员 | 不可自动重试、超过重试上限、金额敏感 | 创建财务待办，通知客服可见 |
| `refund_failed` | `refunding` | 财务管理员 | 修正信息后重新发起模拟退款 | 写财务处理审计 |
| `refund_failed` | `refunded` | 财务管理员 | 线下或人工模拟完成，需二次确认 | 写财务审计，通知双方 |
| `customer_service` | `waiting_buyer_return` | 平台客服 | 裁定退货退款且需用户退货 | 写客服裁定，通知双方 |
| `customer_service` | `refunding` | 平台客服 | 裁定仅退款或无需退货 | 创建退款单；大额需财务复核 |
| `customer_service` | `closed` | 平台客服 | 裁定驳回或用户撤销 | 写客服裁定，通知双方 |

所有用户提交、商家审核、客服裁定、财务处理接口都必须有 `idempotency_key` 或等价幂等标识。重复请求应返回第一次处理结果。

## 6. 退货物流规则

- 用户只能在 `waiting_buyer_return` 状态填写或修改本人退货物流。
- 物流单号、公司、寄出时间必须校验格式；修改物流需记录修改前后值和原因。
- 填写物流后进入 `waiting_merchant_receipt`，系统计算商家确认收货截止时间。
- 商家可在本店售后详情中确认收货、标记未收到、标记商品异常或申请客服介入。
- 商家拒收或标记异常必须填写原因并上传开箱、称重、破损或错寄凭证。
- 用户和客服可以看到物流状态和商家反馈；商家列表页用户手机号、地址默认脱敏。

## 7. 模拟退款规则

M4 模拟退款单状态：

```text
pending
  -> succeeded
  -> failed
  -> manual_review

failed
  -> pending
  -> succeeded
```

退款创建规则：

- 只能由售后状态机从 `refunding` 入口创建，不允许普通用户或商家直接创建退款单。
- 退款金额不得超过订单可退金额、售后审核金额和支付成功金额。
- 部分退款必须锁定对应订单行可退数量和金额，退款成功后释放正在处理额度并写入已退额度。
- 运费、优惠券、积分、组合商品分摊必须保存明细；M4 可先实现基础分摊，但字段不能缺失。
- 大额、频繁退款、风控命中或客服裁定退款可进入财务复核，不得由客服直接完成资金状态。

退款回调规则：

| 回调类型 | 处理规则 |
|---|---|
| 首次成功 | 退款单置为 `succeeded`，售后单置为 `refunded` |
| 重复成功 | 返回已处理，不重复退款、不重复通知 |
| 首次失败 | 退款单置为 `failed`，售后单置为 `refund_failed` |
| 重复失败 | 返回已处理，不重复生成财务待办 |
| 失败后成功 | 若退款单仍可处理且金额匹配，可以成功；否则记录乱序事件 |
| 成功后失败 | 保持成功，记录乱序失败事件 |
| 金额不一致 | 拒绝成功迁移，进入人工复核或异常待办 |
| 售后单不存在 | 记录无主退款回调，通知财务和技术管理员 |

自动重试策略：

- 仅对可重试失败码自动重试，例如临时网络错误、渠道超时、模拟渠道限流。
- 重试必须使用稳定退款请求号和回调事件 ID，不能生成多笔真实退款语义。
- 超过重试上限、金额不一致、账户异常、支付单状态异常必须进入 `refund_failed`。

## 8. 客服介入工单

工单创建场景：

- 商家拒绝后用户申请客服介入。
- 商家审核超时按规则自动升级。
- 商家拒收、物流异常、双方证据冲突。
- 退款失败进入人工处理时需要客服和财务协同。
- 风控命中频繁售后或疑似欺诈。

客服可执行：

- 查看订单、售后、退款、物流和双方证据链。
- 要求用户或商家补充凭证，并设置补充截止时间。
- 裁定商家同意、裁定用户退货、裁定退款、裁定驳回。
- 对小额或规则明确场景发放补偿券。
- 升级给客服主管、风控或财务管理员。

客服禁止：

- 绕过退款单直接把资金状态改为成功。
- 绕过财务复核处理超大金额、风控命中或渠道异常退款。
- 查看与工单无关的完整敏感字段。
- 修改商品、库存、支付流水原始记录。

工单结案必须写入结论、依据、引用证据、用户可见文案、商家可见文案和内部备注。用户和商家只能看到各自可见文案，内部风控和财务备注不得外显。

## 9. 超时任务

超时窗口应由后台配置，测试环境可配置为分钟级。

| 场景 | 起点 | 到期动作 | 说明 |
|---|---|---|---|
| 商家审核超时自动同意 | `merchant_review` 创建或补证后 | 低金额、未发货、规则明确时进入 `refunding` 或 `waiting_buyer_return` | 必须写系统事件和规则快照 |
| 商家审核超时自动升级 | `merchant_review` 创建或补证后 | 高金额、风控命中、证据复杂时进入 `customer_service` | 创建客服工单 |
| 用户超时未退货 | `waiting_buyer_return` 开始 | 进入 `closed` | 保留用户再次申请规则和历史证据 |
| 商家收货超时自动确认 | `waiting_merchant_receipt` 开始，或物流签收后 | 进入 `refunding` | 必须检查商家是否已提交拒收或异常凭证 |
| 证据补充超时 | 客服或商家要求补证后 | 按当前规则关闭、维持拒绝或交由客服裁定 | 不能静默删除证据 |
| 退款失败重试 | `refund_failed` 开始 | 可重试则重新进入 `refunding`，不可重试进入 `refund_failed` | 重试次数和失败码可见 |

超时任务必须：

- 在事务中锁定售后单或退款单。
- 再次读取当前状态，跳过已处理对象。
- 使用任务名称、对象 ID、截止时间作为幂等键。
- 写任务日志、状态事件、审计日志和通知。
- 支持重复执行、断点续扫和失败告警。

## 10. 订单联动

M4 不建议把订单主状态直接改成所有售后细节。订单应保留履约主状态，并增加售后摘要或派生展示态。

| 售后结果 | 订单联动 |
|---|---|
| 售后创建 | 订单详情展示售后处理中入口，商家和管理员订单时间线出现售后事件 |
| 未发货仅退款成功且全单退款 | 订单可进入 `closed`，关闭原因 `refunded_before_shipment` |
| 部分退款成功 | 订单主履约状态不变，订单行更新已退金额和可售后数量 |
| 退货退款成功且全单退款 | 订单展示已退款或售后完成，是否关闭按履约规则配置 |
| 售后关闭或驳回 | 订单恢复可售后状态摘要，保留历史售后记录 |
| 客服介入中 | 用户、商家、管理员订单详情均显示工单状态和下一步动作 |

订单、售后、退款、工单事件必须能在管理员详情页按时间线合并展示。

## 11. 权限与数据范围

| 角色 | 允许动作 | 禁止动作 |
|---|---|---|
| 普通用户 | 查看本人售后，创建本人订单的售后，补充凭证，填写退货物流，申请客服介入，撤销未进入退款的售后 | 查看他人售后，直接创建退款单，修改退款状态，处理商家待办 |
| 商家店主 | 查看本店售后，配置店铺售后处理人员，查看本店退款摘要 | 跨店铺处理，绕过客服裁定，直接改资金状态 |
| 订单客服 | 审核本店售后，同意、拒绝、要求补证，确认收货，申请平台介入 | 查看跨店铺售后，处理财务复核，修改商品价格 |
| 仓储发货 | 查看本店退货物流，登记收货异常凭证，辅助确认收货 | 审核售后诉求，裁定退款，查看财务字段 |
| 商家财务 | 查看本店退款记录、结算影响和对账摘要 | 审核售后、拒绝用户申请、直接改退款状态 |
| 平台客服 | 处理售后工单，查看必要证据，裁定同意、退货、驳回，要求补证 | 直接完成超大金额退款，修改支付流水，处理商家结算 |
| 客服主管 | 处理升级工单、复核批量或高风险裁定 | 直接修改资金流水 |
| 风控审核 | 查看风险售后，标记欺诈风险，冻结高风险退款待复核 | 普通客服裁定、商家结算 |
| 财务管理员 | 查看退款单、失败码、重试记录，处理人工退款复核 | 商品审核、客服裁决、绕过售后单创建退款 |
| 技术管理员 | 查看任务、日志、幂等记录和模拟渠道回调 | 直接处理业务资金或客服裁定 |
| 只读审计 | 查看售后、退款、工单和审计日志 | 任何写操作 |

字段权限：

- 用户可看本人完整收货地址、退货地址和本人联系方式。
- 商家列表页默认脱敏用户手机号和地址；详情页按履约和售后权限展示必要字段。
- 平台客服只能在工单或授权查询场景查看敏感字段，访问必须写审计。
- 财务管理员默认查看金额、支付单、退款单、失败码和渠道流水，不默认查看完整地址。
- 技术管理员查看原始回调时必须屏蔽密钥、令牌和个人敏感信息。

## 13. 审计与事件

必须写售后状态事件：

- 售后创建、补充凭证、撤销。
- 商家同意、拒绝、要求补证。
- 用户填写或修改退货物流。
- 商家确认收货、拒收、标记异常。
- 客服介入、客服裁定、工单结案。
- 用户超时关闭、商家超时自动同意或升级、商家收货超时自动确认。
- 退款创建、成功、失败、重试、人工处理。

必须写审计日志：

- 权限拒绝。
- 商家或管理员读取敏感字段。
- 商家拒绝售后、拒收退货、确认收货。
- 客服裁定、客服主管复核、风控冻结或释放。
- 财务退款重试、人工完成、退款异常处理。
- 技术管理员查看或重放模拟渠道回调。
- 金额不一致、退款单不存在、重复或乱序回调。

事件字段至少包含：

- `actor_type`：`user`、`merchant_user`、`admin_user`、`system`、`mock_refund_channel`。
- `actor_id`：系统任务可为空，但必须记录任务名。
- `source`：Web、Android、merchant console、admin console、system job、callback。
- `object_type` 和 `object_id`。
- `before_status`、`after_status`。
- `reason_code`、用户可见文案、内部备注。
- `evidence_ids` 或证据摘要。
- `request_id`、`idempotency_key`、IP、User-Agent。
- `created_at`。

## 14. 多端联动

| 状态变化 | 用户端 | 商家后台 | 管理员后台 |
|---|---|---|---|
| 售后创建 | 展示待商家处理、处理截止时间 | 进入售后待处理队列，显示剩余时间和风险等级 | 客服可只读查看，风控可观察异常 |
| 商家同意仅退款 | 展示退款处理中 | 该售后从待审核转为退款跟踪 | 财务可见退款单 |
| 商家同意退货退款 | 展示填写退货物流入口和截止时间 | 展示待买家退货 | 客服可查看时间线 |
| 商家拒绝 | 展示拒绝原因、补证和客服介入入口 | 显示已拒绝和后续用户动作 | 客服可查看争议候选 |
| 用户补充凭证 | 展示已补充、等待商家处理 | 重新进入审核待办 | 客服可查看证据链 |
| 用户填写物流 | 展示待商家收货 | 进入待确认收货队列 | 客服可查看物流 |
| 商家确认收货 | 展示退款处理中 | 展示待退款或已转财务 | 财务可见退款单 |
| 退款失败 | 展示退款处理中或异常处理中，不暴露内部失败细节 | 展示退款异常只读状态 | 财务和技术看到失败码和重试 |
| 客服介入 | 展示平台处理中和待补证动作 | 展示工单状态和商家待补证动作 | 进入客服工作台 |
| 售后关闭 | 展示关闭原因和可再次申请规则 | 展示关闭原因 | 审计可查看完整历史 |

用户端和 Android 必须展示当前阶段、下一步动作、截止时间和用户可理解原因。商家后台必须支持按处理状态、超时风险、金额、原因、物流状态筛选。管理员后台必须按角色展示客服工单、退款异常、风控风险和审计日志。
